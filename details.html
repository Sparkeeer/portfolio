Automation, flagship

Mail-to-Ticket System

The shared support mailbox was a general inbox. Real requests sat next to monitoring alerts, quarantine digests, vendor threads, project mail and marketing. I turned it into a ticketing system in Dynamics 365 Customer Service, so every real request becomes a tracked, classified and routed case. About 80% less manual ticket work, and first response in under 10 minutes.

  1. Email arrives
  2. ARC rule filters
  3. Case created or threaded
  4. Classified
  5. Power Automate routes
  6. Agent works the case

1. Mail intake

  • Connected the shared support mailbox to a Dynamics queue with server-side synchronization for incoming and outgoing mail.
  • Set up an Automatic Record Creation (ARC) rule so a case is created whenever the support address is in To or Cc.
  • Kept the original mail in the mailbox, so nothing is lost if a rule changes.

2. Noise filtering

  • Studied what actually lands in the mailbox, then replaced broad keyword filters with precise ones. "alert" and "noreply" were blocking real requests.
  • The rule now skips monitoring-tool alerts, quarantine digests, webinars and unsubscribe/marketing mail before any case is created.
  • Tested with mail that should and shouldn't become cases, and checked each result in the ARC Activity Monitor.

3. Threading and no duplicates

  • Turned on email correlation, tracking tokens and smart matching, so replies attach to the existing case instead of opening a new one.
  • Stopped duplicate timeline entries caused by mail being tracked twice between internal users.

4. Classification model

  • Built all changes in a dedicated solution on the standard Case table, so they can be moved between environments.
  • Work Type (Incident, Service Request, Monitoring Alert, Project Work, Vendor Escalation, Security Event, Administrative/FYI, Manual Review), plus Category, Source Type, Waiting On and Impact Scope.
  • Vendor Ticket ID and Related Project fields, plus monitoring fields: alert device, alert state, first/last detected, recovery received.

5. Routing and rules

  • Three review queues (Manual Review, Monitoring Review, Project & Vendor Review) behind a routing ruleset.
  • A Power Automate flow that routes each case by Work Type, and another that keeps Status Reason in sync with Waiting On. I used a flow because business rules can't reliably set status.
  • Business rules require the right fields for vendor escalations, project work and monitoring alerts.

6. Agent experience

  • Reworked the case form into a 35/65 layout so the timeline and Copilot panel have room. Removed panels nobody used.
  • Turned on Copilot case summaries and email drafting.
  • Rebuilt the case views around Status Reason, Waiting On, Work Type and Impact Scope, with newest cases first.

7. Hardening

  • Fixed internal staff being recorded as the customer on cases.
  • Turned on auditing after a case went missing, so every change can be traced.

Infrastructure, migration

Biometric Access & Cloud Attendance

Deployed a face and fingerprint terminal for an office of 20+ employees, then moved the whole setup from a locally hosted server to a cloud platform, so management no longer depends on one workstation staying online.

  1. Terminal setup
  2. Local server
  3. Data migration
  4. Cloud platform
  5. Mobile and reports
  • Configured the terminal's network, time and biometric enrolment, with anti-spoofing on. Face or fingerprint is accepted, so nobody has to use both.
  • Built daytime, overnight and cross-midnight attendance schedules with different weekly offs per group. First-in and last-out logic stops stray mid-shift detections from distorting worked hours.
  • Queried the device directly over ISAPI with Digest authentication to check records, credential counts and group mappings. Testing showed people and permissions sync but department structures do not, so no risky changes went to production.
  • Fixed an incident where the terminal was online but events stopped reaching the server. The cause was a stale event channel held by the wrong client. A controlled restart restored live events, and the missed history was recovered from the device with no reset and no re-enrolment.
  • Migrated employees, departments and credentials to the cloud platform by reshaping the export into its import format, matching on employee ID to avoid duplicates.
  • Proved the cloud path by stopping the local services and confirming new events still arrived automatically.
  • Corrected a 10.5-hour timestamp offset by standardising on IST and disabling daylight saving on the device.
  • Enabled mobile check-in with photo verification for approved work-from-home staff, separated administrator, manager and employee roles, and turned off automatic overtime to prevent false records from repeated detections.

Architecture, advisory

Consolidating seven tenants under one brand

SituationAn organisation with seven Microsoft 365 tenants wanted everything under one company name.

  • Laid out the two real options: a Multitenant Organization (shared communication, tenants stay separate) or a full tenant-to-tenant migration (one tenant, one identity).
  • Found the licensing gap early: MTO cross-tenant sync needs Entra ID P1, and the tenants were on Business Basic.
  • Recommended a pilot group first, with MTO as a coexistence stage if they later migrate.

Migration, live cutover

Mail cutover with locked DNS records

SituationDuring a live Google Workspace to Microsoft 365 cutover, the old Google MX records couldn't be deleted at the registrar, leaving mail split between two providers.

  • Told apart harmless leftover records and the ones that break mail (MX, SPF).
  • Traced the lock to a mail service still linked to the domain, and worked with the domain owner during the call to clear it.
  • Ran a final delta sync after cutover and kept the source tenant alive as a fallback.
