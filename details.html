Cross-Tenant M365 Migrations

Moved organisations' mail, OneDrive and SharePoint from one Microsoft 365 tenant to another, including US-to-India moves for compliance.

Problem
Organisations needed to move to a new tenant, some for compliance
What I did
Pre-sync, DNS cutover, delta sync and checks with AvePoint Fly
Result
3+ tenants migrated, zero data loss
How I ran it
  1. Assess
  2. Prepare target
  3. Pre-sync
  4. Cutover
  5. Delta sync
  6. Validate

1. Assessment and scope

  • Listed what had to move: mailboxes, OneDrive, SharePoint sites and libraries, Teams chat and any shared mailboxes.
  • Separated Teams teams (channels and files) from private chats, since migration tools handle and license them differently.
  • Confirmed data sizes and the cutover date with the client before work started.

2. Preparing the target tenant

  • Migration tools move content, not identities, so I created every user in the target tenant first and assigned licences.
  • Built a one-to-one mapping from each source account to its new target account.
  • Recreated groups and shared mailboxes with matching permissions.

3. Pre-sync and cutover

  • Ran a staged pre-sync with AvePoint Fly while users kept working in the old tenant, so most data was moved before cutover day.
  • On cutover, moved the domain and updated MX, SPF, Autodiscover and DKIM so new mail landed in the target tenant.
  • Ran a final delta sync to catch anything that arrived during the switch.

4. Validation and handover

  • Checked item counts, mailbox permissions and file access, and sent test mail in both directions.
  • Watched mail flow with message trace for the first days after cutover.
  • Kept the source tenant active as a fallback until everything was confirmed.

5. Documentation

  • Wrote an internal SOP and step-by-step runbook for AvePoint cross-tenant migrations, plus a pre- and post-migration checklist, so each new migration follows the same steps.

Migration, live cutover

Google Workspace → Microsoft 365

Migrated a 40-user company's mail, calendar, contacts and Drive files to Microsoft 365, and ran the cutover on a live call with the client.

Problem
40 users moving off Google while the business kept running
What I did
Data migration plus a live DNS cutover with the client
Result
No break in email delivery
How I ran it
  1. Migrate data
  2. Final delta sync
  3. DNS cutover
  4. Fix conflicts
  5. Monitor
  6. Retire Google

1. Moving the data

  • Moved Gmail, Calendar and Contacts into Exchange Online, and Drive files into OneDrive and SharePoint.
  • Ran delta syncs right up to cutover so nothing sent in the meantime was missed.

2. DNS cutover

  • Used the Microsoft 365 domain setup with the registrar's automatic DNS option to add MX, Autodiscover, SPF and DKIM records.
  • Separated harmless leftover records from the ones that actually break mail. Only MX and SPF had to be replaced.

3. Fixing a blocked cutover

  • The domain health check flagged five old Google MX records still active next to Microsoft's, which would have split incoming mail between two providers.
  • The registrar refused to delete them. I traced the lock to a mail service still linked to the domain, then cleared it with the domain owner during the call.
  • Merged SPF into a single Microsoft record, since two SPF records make outgoing mail fail checks.

4. After cutover

  • Ran a final delta sync a few hours later to pick up mail that reached Gmail while DNS changes spread.
  • Kept Google Workspace running for about two weeks as a safety net, then retired it once mail flow was stable.
  • Handled follow-up requests such as changing a user's primary address while keeping the old one as an alias.
  • Exchange Online
  • OneDrive
  • DNS
  • MX / SPF / DKIM

Employee Engagement Bot

Automated birthday and work-anniversary recognition with Teams posts, branded HTML emails, and a Copilot Studio bot employees can ask about upcoming celebrations.

Problem
Celebrations tracked by hand, and private data at risk in the bot
What I did
Scheduled flows plus a Copilot Studio bot backed by a tool flow
Result
Fully automated, with private details never exposed
How I built it

Data and daily automation

  • An Employee Directory in a SharePoint list, bulk-loaded from Excel.
  • Scheduled Power Automate flows check the list every day, post in Teams and send a branded HTML email. I later redesigned the email to look more modern.

The bot

  • Published the bot to the Teams app catalog for the whole company and fixed access problems for individual users.
  • Wrote clear agent instructions: a "fetching details" status message, no links or private details, no guessing, and other topics sent to IT Support.

Privacy fix

  • With SharePoint as a knowledge source, each user needed access to the list itself, which would have exposed private employee information. It also showed source links in answers.
  • Replaced it with a Power Automate tool flow that reads the list on its own connection and returns only the fields the bot needs.

Consolidating seven tenants under one brand

An organisation with seven Microsoft 365 tenants wanted everything under one company name.

Situation
Seven tenants, one company name
What I did
Compared MTO with a full migration and found the licensing gap
Recommendation
Start with a pilot group
How I approached it
  • Laid out the two real options: a Multitenant Organization (shared communication, tenants stay separate) or a full tenant-to-tenant migration (one tenant, one identity).
  • Found the licensing gap early: MTO cross-tenant sync needs Entra ID P1, and the tenants were on Business Basic.
  • Recommended a pilot group first, with MTO as a coexistence stage if they later migrate.
